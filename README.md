# VLESS-подписка для v2rayNG: автоматическая сборка на GitHub Pages

Один постоянный URL, который каждые 6 часов пересобирается в GitHub Actions из
публичных источников: скачивание → разбор → валидация → дедупликация → проверка
доступности → публикация на GitHub Pages.

**Ссылка для клиента:**

```
https://USERNAME.github.io/vless-sub/sub.txt
```

Замените `USERNAME` на свой логин GitHub (после первого запуска workflow ссылка
печатается в логе шага `deploy` и на вкладке Pages в настройках репозитория).

---

## Что публикуется

| Файл | Что внутри |
|---|---|
| `docs/sub.txt` | base64-подписка: только узлы, через которые реально прошёл запрос (до 800) |
| `docs/sub-plain.txt` | тот же список строками `vless://…` |
| `docs/sub-all.txt` | всё, что прошло валидатор, включая непроверенные (до 2000) |
| `docs/status.json` | время сборки, счётчики, состояние каждого источника |
| `docs/index.html` | страница со ссылками и статистикой |

`sub.txt` — то, что вставляют в v2rayNG. `sub-all.txt` — запасной вариант, если
нужен максимальный выбор и не смущает наличие мёртвых узлов.

## Структура репозитория

```
sources.txt                  список публичных источников (1 URL = 1 строка)
scripts/merge.py             сборщик: fetch, decode, validate, dedup, probe, publish
scripts/private_uri.py       локальный конвертер собственной подписки в URI (не публикует)
.github/workflows/update.yml расписание / ручной запуск / пересборка при правке
docs/                        ТОЛЬКО результат сборки; именно она уходит на Pages
```

Исходники и результат физически разделены: Pages публикует каталог `docs/`,
поэтому `sources.txt` и скрипты на сайте не появляются.

## Как работает сборщик

1. **Загрузка.** Каждый URL из `sources.txt` скачивается отдельно, с таймаутом 30 с,
   User-Agent `v2rayNG/1.9.16` и до 3 попыток. Лимит 16 МБ на источник.
2. **Разбор формата** — автоматически: plain-текст, base64-блоб или JSON-массив
   Xray-конфигов (`[{"outbounds":[…],"remarks":"…"}]`).
3. **Валидация.** Для VLESS проверяются: UUID в userinfo, порт 1–65535, `encryption=none`,
   `security ∈ {none,tls,reality,xtls}`, `type` из известных сетей (`tcp`, `ws`, `grpc`,
   `h2`, `http`, `httpupgrade`, `xhttp`, `splithttp`, `quic`, `kcp`), наличие `pbk`
   при `security=reality`, корректность `flow`. Строки с localhost/приватными IP
   отбрасываются. Нераспознанные схемы (socks/http) отсеиваются, а не ломают сборку.
4. **Дедупликация** в два уровня: точное совпадение строки и «отпечаток» конфига
   (протокол + UUID + хост + порт + security + сеть + sni + path + pbk + sid + flow).
   Второй уровень убирает один и тот же сервер с разным порядком параметров
   или разным `#именем`.
5. **Лимит на хост** — не больше 4 конфигов с одного IP/домена, чтобы одна щедрая
   ферма не заняла всю подписку.
6. **Грубая проверка** — реальный TCP-connect (для `security=tls|reality` ещё и
   TLS-handshake с нужным SNI), 48 параллельно, таймаут 4 с. Отсекает закрытые порты.
7. **Проверка трафиком (главный фильтр).** Каждый узел, прошедший шаг 6, поднимается
   настоящим клиентом Xray на локальном HTTP-порту, и через него отправляется запрос
   `http://cp.cloudflare.com/generate_204` (при неудаче — второй target). Конфиг,
   через который ответ не пришёл, считается нерабочим. Именно этот шаг убирает узлы
   с отозванными UUID, неверными REALITY-ключами и перегруженные Cloudflare-Worker'ы,
   которые «отвечают» на TCP, но трафик не пропускают. 10–12 параллельных воркеров.
8. **Публикация.** В `sub.txt` попадают только узлы, прошедшие шаг 7 (сначала свой
   приватный источник, затем по задержке). Всё остальное — в `sub-all.txt`.
9. **Коммит (только в CI).** Если задан `GITHUB_ACTIONS=true`, сборщик коммитит
   `docs/` обратно в репозиторий, чтобы следующая сборка могла сравнить результат
   с предыдущим. Локальный запуск ничего не коммитит (`--no-publish-commit` отключает
   это и в CI).

### Что скачивается ради шага 7

Один официальный релиз Xray-core (`XTLS/Xray-core`), версия **закреплена** в
`scripts/xray_check.py` вместе с **sha256**, который проект публикует в своём
`.dgst`-файле. Архив проверяется по хешу до распаковки; при несовпадении сборка
не запускает бинарник и деградирует к TCP-результатам. Ничего другого не
скачивается, никакие скрипты из репозиториев-источников не исполняются.
Отключить: `DEEP_TEST=0` (или `--no-deep`).

### Чего проверка НЕ делает

* **География.** Xray крутится на раннере GitHub (США/ЕС), а вы — в России.
  Узел, который прошёл проверку там, может быть недоступен отсюда, и наоборот:
  блокировки на пути «Россия → узел» этот тест не видит. Поэтому `sub.txt` —
  «работает из сети раннера», а не «гарантированно работает у вас». Для точной
  картины используйте в v2rayNG «Реальную задержку» (см. ниже).
* **Скорость и стабильность.** Проверяется факт прохождения одного HTTP-запроса,
  а не пропускная способность и не устойчивость под нагрузкой.
* **Лимиты и блокировки на стороне провайдера.** Узел может пустить один запрос
  и закрыться при потоке.
* **Обход ограничений.** Ни белые списки, ни блокировки не проверяются и не
  обещаются: тест отвечает только на вопрос «трафик через этот конфиг проходит
  или нет».

### Проверка на своём устройстве

В v2rayNG: долгое нажатие на группу подписки → **«Тест реальной задержки»**
(Real delay). Узлы, у которых задержка не определилась, — мёртвые именно из вашей
сети; удалите их или пересоберите подписку. Это единственный способ узнать
реальную картину для вашего оператора.

Замечания по этим репозиториям:

  но фактически содержит только `socks5`/`http`/`socks4` (2260/1733/5 строк) —

* `trikiman/vlessfilter` публикует также `subs/all.txt` со всеми протоколами;
  мы берём VLESS-вариант, чтобы подписка оставалась однородной.

## Безопасность

* **Никакого исполнения чужого кода.** Скачивается только текст. Скрипты из
  сторонних репозиториев не запускаются, команды из конфигураций не выполняются,
  xray и прочие бинарники не загружаются.
* **Секреты не попадают в репозиторий.** Приватная подписка передаётся только через
  `secrets.PRIVATE_SUB_URL` и по умолчанию **не используется** (см. ниже).
  В лог печатаются только счётчики, URL приватного источника маскируется.
* **Pages публикует только `docs/`.** Ни `sources.txt`, ни `scripts/`, ни
  `.github/` на сайте недоступны.
* **Логи публичного репозитория видны всем** — поэтому сборщик никогда не печатает
  содержимое конфигураций, только агрегаты. Учитывайте это, включая приватный источник.

## Личные подписки

**Текущий статус: приватный источник включён** (`INCLUDE_PRIVATE=true`). В сборку
подмешивается подписка Aiden VPN — 14 узлов (12 REALITY + 2 TLS), все проходят
проверку доступности и стоят в начале `sub.txt`. Токен хранится только в секрете
репозитория: ни в `docs/`, ни в `status.json`, ни в логах его нет.

Ниже — история проверки второй подписки, которая в сборку не попала.

Проверено 2026-10-18 на личной подписке автора репозитория:

* `User-Agent: v2rayNG` (и `v2raytun`, `sing-box`) → JSON-массив Xray-конфигов;
* `User-Agent: Happ` → base64-подписка;
* заголовки: `subscription-userinfo` (израсходовано ≈20 ГБ из 100 ГБ, срок до 2026-10-20)
  и `profile-title` с названием сервиса.

**Во всех вариантах конфиг один и тот же и он нерабочий:** VLESS-аутбаунд указывает
на приватный адрес и порт `1` — это заглушка, а не сервер. TCP-подключение к нему,
естественно, не устанавливается, валидатор такие адреса отбрасывает.

Отсюда два вывода:

1. Публиковать нечего — реальных узлов подписка сейчас не отдаёт. Токен при этом
   нигде не засветился: в репозиторий, в `docs/` и в логи он не попал.
2. Сначала стоит выяснить у провайдера, почему вместо сервера приходит заглушка
   (типичные причины: исчерпан лимит устройств, подписка не активирована, сменился
   формат выдачи). Заодно проверьте срок: он истекает 2026-10-20.

Если провайдер начнёт отдавать нормальный конфиг, включить его в общую ссылку можно
двумя шагами — но **только осознанно**, см. следующий раздел.

### Если всё-таки хотите объединить (не рекомендуется)

GitHub Pages на бесплатном тарифе работает только для **публичных** репозиториев.
Значит, любой узел, попавший в `docs/sub.txt`, становится доступен всему интернету —
включая ваши платные учётные данные (UUID/пароль). Это почти наверняка нарушает
правила провайдера и может привести к блокировке аккаунта или исчерпанию трафика
чужими руками. Токен подписки при этом остаётся секретным, но сами серверы — нет.

Если это приемлемо:

1. Settings → Secrets and variables → Actions → **Secrets** → `PRIVATE_SUB_URL` = ваша ссылка.
   Несколько подписок можно перечислить в одном секрете через запятую, пробел или
   перевод строки — каждая станет отдельным источником (`<private-1>`, `<private-2>`).
2. Там же → **Variables** → `INCLUDE_PRIVATE` = `true`.

Без второго шага приватный источник игнорируется, даже если секрет задан.

Узлы из приватного источника ставятся в начало `sub.txt` и не вытесняются лимитом
`--max-configs`: сортировка идёт по признаку (ответил на проверку → приватный →
задержка). В `status.json` такой источник виден как `<private>`, его URL и токен
в лог и в файлы не попадают — в том числе в тексте ошибок.

Более безопасная альтернатива — держать личную подписку **отдельно** в v2rayNG:

* если провайдер отдаёт URI/base64 — добавьте её второй подпиской, обновляется сама;
* если отдаёт JSON (как сейчас) — v2rayNG не умеет подписываться на JSON-массив;
  конвертируйте локально:

```bash
python scripts/private_uri.py --url "https://<ваш-провайдер>/<TOKEN>" --out local_private.txt
```

Файл `local_private.txt` в `.gitignore`, никуда не отправляется; импортируйте его
в v2rayNG через «+» → «Импорт конфигурации из файла». Обновлять придётся вручную.

## Локальный запуск

```bash
python scripts/merge.py                     # сборка в docs/ (нужен только Python 3.9+)
python scripts/merge.py --dry-run           # посчитать, ничего не записывая
python scripts/merge.py --no-probe          # без проверки доступности (быстро)
python scripts/merge.py --max-configs 300   # сколько узлов в sub.txt
python scripts/merge.py --allow-protocols vless,vmess,trojan,ss   # расширить набор
```

Зависимостей нет — только стандартная библиотека.

## Автоматизация

`.github/workflows/update.yml`:

* `schedule: "17 */6 * * *"` — каждые 6 часов (UTC; GitHub может задержать запуск);
* `workflow_dispatch` — кнопка **Run workflow**;
* `push` в `main` при изменении `sources.txt`, `scripts/**`, самого workflow;
* `concurrency: pages` — одновременные сборки выстраиваются в очередь;
* `timeout-minutes: 30` — сборка не может «съесть» час минут.

Если две сборки всё же пересекутся (например, ручной запуск совпал с плановым),
коммит `docs/` делает сам `scripts/merge.py`: он делает `fetch` + `reset` на
актуальный `origin/main`, коммитит поверх и повторяет `push` до трёх раз. Поэтому
гонка не приводит к `! [rejected] main -> main`. Шаг `Commit refreshed files`
в workflow остаётся страховкой: если содержимое уже закоммичено, он просто
сообщает `no changes to commit`.

Публикация: `upload-pages-artifact` (каталог `docs`) → `deploy-pages`. Pages
настроен на источник **GitHub Actions**, поэтому на сайт попадает ровно то, что
собрал workflow, а не содержимое ветки.

Лимиты бесплатного тарифа (проверено 2026-10-18):

* Actions: минуты для публичных репозиториев не тарифицируются; типичная сборка
  здесь — 1,5–2 минуты;
* Pages: сайт до 1 ГБ, мягкий лимит 100 ГБ трафика в месяц и 10 сборок в час;
  наша страница — сотни килобайт, сборок 4 в сутки.

Отдельный нюанс: GitHub отключает **scheduled** workflow в публичных репозиториях
после 60 дней без активности. Здесь workflow сам коммитит `docs/`, поэтому
активность есть; если расписание всё же отключится — GitHub пришлёт письмо,
достаточно нажать «Enable workflow».

## Защита от порчи результата

| Ситуация | Поведение |
|---|---|
| один источник недоступен | сборка продолжается, в `status.json` пишется ошибка |
| недоступны все источники | код выхода 2, `docs/` не трогается, сайт остаётся прежним |
| конфигов меньше `MIN_CONFIGS` (20) | код выхода 3, предыдущая подписка сохраняется |
| число конфигов упало более чем вдвое | код выхода 3, предыдущая подписка сохраняется (`--force` отменяет) |
| проверка доступности не дала ничего | публикуется полный список + предупреждение на `index.html` |

Так как `docs/` лежит в git, предыдущая удачная сборка всегда доступна — в том
числе из истории коммитов.

## Подключение в v2rayNG (Android)

1. Установите v2rayNG (Google Play, F-Droid или APK с GitHub-релизов).
2. Меню (☰) → **Группы подписок** → **+** (справа сверху).
3. В поле **URL** вставьте `https://USERNAME.github.io/vless-sub/sub.txt`.
4. **Сохранить** (галочка). Подписка появится в списке.
5. Нажмите на неё → **Обновить подписку** (или значок обновления). Загрузятся конфиги.
6. Выберите любой узел → кнопка подключения (V) в правом нижнем углу.
7. Автообновление: в настройках подписки включите **Автообновление** (Auto update)
   и интервал; либо обновляйте вручную — файл на сервере меняется каждые 6 часов.

Если узлы не появились: проверьте, что ссылка открывается в браузере телефона
(должна скачаться base64-строка, а не 404), и что в подписке не включён
«фильтр по протоколу», скрывающий VLESS.

## Ограничения, о которых стоит помнить

* Публичные конфигурации принадлежат третьим лицам. Их работа, скорость, логи и
  добросовестность владельцев не гарантируются.
* Бесплатные узлы живут недолго: часть умрёт между сборками, поэтому подписка
  обновляется часто, а `sub-all.txt` держит запас.
* Через такие узлы не стоит проводить банковские операции и передавать
  чувствительные данные.
* Проект не предназначен для обхода запретов, установленных законом или
  оператором сети; он лишь собирает публично доступные конфигурации и проверяет
  их техническую доступность.
