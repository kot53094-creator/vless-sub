# Перенос на другого провайдера

Цель: лимит одного сервиса не должен останавливать сервис целиком. Здесь —
что переносится, чем именно, и как проверить, что данные доехали.

## Что переносится, а что нет

| Слой | Переносится | Как |
|---|---|---|
| Данные (люди, серверы, платежи) | **да** | экспорт `/api/export` → Turso/Postgres |
| Кэш и объединённый пул | нет (это кэш) | пересобирается синхронизацией |
| Код воркера | **да** | `runtime/node/` — тот же обработчик на Node 22 + SQLite, проверено |
| Секреты | вручную | `wrangler secret put` на новом месте |
| VPN-узлы | не на serverless | отдельные серверы, к платформе не относятся |

Ключевая мысль: лимиты, в которые мы упираемся, — это **D1 (строки) и KV
(записи)**. Перенос базы снимает первую и самую жёсткую. KV остаётся только
как кэш: потеря пула не ломает выдачу, её пересоберёт синхронизация.

## Вариант A. Turso (рекомендуется, тот же SQLite)

Turso — libSQL, диалект SQLite. Схема и запросы переносятся без правок,
переключение — два секрета.

```bash
# 1. Создать базу (бесплатный тариф, карта не нужна)
turso db create apelsinka

# 2. Забрать схему из текущей D1
npx wrangler d1 export vpn-hub-lite --remote --no-data --output backups/schema.sql
turso db shell apelsinka < backups/schema.sql

# 3. Забрать данные
npm run db:export:portable -- --url https://<воркер> --token $CHECK_TOKEN \
  --scope critical --format sql --dialect sqlite --out backups/data.sql
turso db shell apelsinka < backups/data.sql

# 4. Проверить, что строки совпали
turso db shell apelsinka "SELECT 'users', COUNT(*) FROM users
  UNION ALL SELECT 'servers', COUNT(*) FROM servers
  UNION ALL SELECT 'sources', COUNT(*) FROM sources;"

# 5. Переключить воркер
npx wrangler secret put TURSO_URL     # libsql://apelsinka-<логин>.turso.io
npx wrangler secret put TURSO_TOKEN
npx wrangler deploy
```

После шага 5 все чтения и записи идут в Turso (`src/db.ts`), D1 больше не
расходует квоту. Откат — удалить два секрета и задеплоить: код вернётся к D1,
данные в D1 останутся на момент переключения.

Проверка после переключения:

```bash
curl -s https://<воркер>/api/v1/status | head -20     # 200, не 503
curl -s https://<воркер>/sub/<токен> | base64 -d | head -3
```

## Вариант B. Postgres (Neon или Supabase)

Даёт независимую от Cloudflare базу и настоящие транзакции. Что готово:

- данные выгружаются в синтаксисе Postgres:
  `--format sql --dialect postgres` (`$`-плейсхолдеры не нужны, это литералы,
  `INSERT ... ON CONFLICT DO NOTHING`);
- схема переносится вручную: SQLite-типы (`TEXT`, `INTEGER`) заменяются на
  `text`, `bigint`, `timestamptz`, `jsonb`; `AUTOINCREMENT` → `GENERATED BY
  DEFAULT AS IDENTITY`.

Чего нет и что нельзя обещать без отдельной работы:

- в коде запросы используют `?`-плейсхолдеры и SQLite-функции
  (`datetime('now')`); для Postgres нужен адаптер диалекта в `src/db.ts`;
- Worker не открывает TCP к Postgres — нужен Hyperdrive (бесплатно
  100 000 запросов в сутки) или HTTP-драйвер Neon;
- `INSERT OR REPLACE` заменяется на `ON CONFLICT ... DO UPDATE` с явным
  списком полей.

Поэтому Postgres — следующий шаг после Turso, а не первый. Триггеры переезда
описаны в `PLATFORM.md` (раздел 3).

## Вариант C. Перенос самого приложения

Код написан под Workers: `fetch(request, env)`, биндинги D1/KV, cron-события.
Чтобы поднять его на VPS/Render, нужен адаптер:

1. HTTP-сервер, вызывающий тот же `fetch` (Node 20 + `undici`);
2. замена `env.DB` на SQLite-файл или libSQL-клиент;
3. замена `env.CACHE` на таблицу `kv` в той же базе;
4. перенос cron в системный планировщик.

Базовый вариант **реализован и проверен** (`runtime/node/`, см.
[SELF-HOSTING.md](SELF-HOSTING.md)): тот же обработчик работает на Node 22 +
SQLite, `/sub` и `/groups` отвечают 200. Не реализованы несколько инстансов,
Postgres и Workers AI вне облака.

## Лимиты: что снимается, а что остаётся

| Ресурс | Cloudflare D1 Free | Turso Free | Neon Free |
|---|---|---|---|
| Чтение | 5 млн строк/сутки | **500 млн строк/месяц** | входит в 100 CU-часов |
| Запись | 100 тыс. строк/сутки | **10 млн строк/месяц** | входит в 100 CU-часов |
| Объём | 5 ГБ | 5 ГБ | 1 ГБ |
| Восстановление | нет | 1 день (PITR) | ветки и история |
| Карта | не нужна | не нужна | не нужна |

После переноса базы остаются лимиты Worker (100 тыс. запросов и 10 мс CPU) и
KV (1 000 записей в сутки). Первый снимается тарифом $5/мес при росте, второй
— уменьшением числа записей кэша (TTL, общий ключ вместо персонального).

## Проверка переноса

Обязательный минимум перед переключением:

1. `manifest.criticalComplete: true` в экспорте;
2. число строк совпало по `users`, `servers`, `sources`, `plans`, `payments`;
3. `/api/v1/status` отвечает 200 на новой базе;
4. `/sub/<токен>` отдаёт непустой список;
5. бот отвечает на `/start` и `/key`;
6. старую базу не удалять минимум неделю.

Скрипт `tools/portable-export.mjs --verify` проверяет пункты 1–2 и структуру
файла, пригодную для `tools/restore-backup.mjs`.

## Безопасность

Экспорт содержит токены подписок и ссылки источников. Каталог `backups/` в
`.gitignore`; файлы не публиковать, после переноса удалять. Доступ к
`/api/export` закрыт `CHECK_TOKEN` — тем же, что у проверок.
