# Архитектура

Проект — агрегатор сторонних VLESS + REALITY конфигураций. Своих VPN-серверов
нет: система собирает ключи из источников, разбирает их, фильтрует, проверяет
и выдаёт каждому пользователю персональную подписку.

Всё работает в одном Cloudflare Worker. Отдельного бэкенда, контейнеров и
платной инфраструктуры нет.

```
                     ┌──────────────────────────────┐
Telegram ──webhook──▶│                              │
Happ ──GET /sub/────▶│        Worker (fetch)        │──▶ D1  (данные)
Браузер ──/admin────▶│                              │──▶ KV  (кэш подписок)
API-клиент ─/api/v1─▶│                              │
                     └──────────────┬───────────────┘
                                    │ cron
                     ┌──────────────┴───────────────┐
                     │ sync   0 */6 * * *           │
                     │ health */20 * * * *          │
                     │ bot    * * * * *             │
                     └──────────────┬───────────────┘
                                    │
                    GitHub Actions / локальный ПК
                    Xray + curl ──POST /api/checks──▶ Worker
```

## Компоненты

| Слой | Что используется | Почему |
|---|---|---|
| Выполнение | Cloudflare Workers, бесплатный план | без карты, без VPS, глобальная сеть, 100 000 запросов в сутки |
| Данные | D1 (SQLite) | SQL, миграции, внешние ключи, бесплатно 5 ГБ |
| Кэш | Workers KV | готовые тела подписок, TTL 600 с |
| Планировщик | Cron Triggers | 3 триггера из 5 доступных |
| Бот | Telegram Bot API | webhook с секретом, резервный polling |
| Интерфейс | серверный HTML из Worker | не нужен отдельный хостинг и сборка frontend |
| Проверка туннеля | Xray-core вне Worker | Worker не может запустить Xray |

## Поток запроса подписки

1. `GET /sub/<токен>` → поиск пользователя по токену, сравнение за постоянное время.
2. Проверка статуса: `pending`, `banned`, `expired`, истёкший срок.
3. `touchDevice` — регистрация устройства по хэшу User-Agent; если устройство
   заблокировано, отдаётся заглушка с причиной.
4. Кэш `sub:v2:<токен>` (KV). Заголовок `subscription-userinfo` всегда
   пересчитывается из базы, чтобы Happ не показывал «безлимит».
5. Выборка серверов (`SERVER_SQL`): только выданные этому человеку, только
   `shareable`-источники, без `paid_private`, с учётом слотов источников.
6. Фильтры: `enabled`, тариф (`personal` — только владельцу), `isModern`,
   режим (`reality`, `working`, `best`, `stable`, `low-latency`, `untested`).
7. Сортировка `compareServers`: ручной приоритет → тип → стабильность
   туннельных проверок → задержка.
8. Сборка Base64, снимок состава в `sub_versions`, запись кэша.

## Поток импорта

`runSync` (раз в 6 часов, 2 источника за прогон):

1. выбор источников, у которых `last_sync_at` старше 6 часов;
2. скачивание с таймаутом 10 с, ограничением 300 КБ, фиксированным UA;
3. `scanSubscription` — разбор, дедупликация, подсчёт причин отказа;
4. `UPSERT` серверов пачками, отсутствующие в источнике помечаются `dead`;
5. `recordImportRun` — статистика прогона в `import_runs`;
6. `autoPool` — раскладка новых серверов по пулам.

Ошибка на любом шаге не удаляет уже сохранённые серверы.

## Поток проверки

Два независимых уровня, которые нельзя смешивать:

| Уровень | Кто выполняет | Что доказывает | Поле |
|---|---|---|---|
| Порт | `health.ts`, cron */20 | адрес отвечает по TCP | `latency_ms`, `last_check_at`, `server_checks.kind='tcp'` |
| Туннель | Xray-агент, `POST /api/checks` | трафик реально проходит через узел | `verified_latency_ms`, `verified_at`, `server_checks.kind='tunnel'` |

Правила:

- рейтинг (`stability`) считается **только** по `kind='tunnel'`;
- одна неудача туннеля ставит `unknown`, две подряд — `dead`;
- успех ставит `alive` и задержку;
- в `server_checks` хранится история, по ней считается стабильность;
- Worker не запускает Xray и не притворяется, что проверяет туннель сам.

## Данные

| Таблица | Назначение |
|---|---|
| `users` | аккаунты Telegram, статус, срок, тариф, токен подписки |
| `sources` | источники: URL или одиночный ключ, тип, видимость, слоты |
| `servers` | конфигурации: ссылка, хост, порт, статус, приоритет, гео |
| `assignments` | какие серверы выданы какому пользователю |
| `pools`, `pool_servers`, `user_pools` | группировка серверов |
| `server_checks` | история проверок с полем `kind` (`tcp`/`tunnel`) |
| `import_runs` | разбор прогонов: строки, принятые, отклонённые, причины |
| `sub_versions` | снимки состава подписки для отката |
| `user_devices` | устройства и их блокировка |
| `fetch_log` | хэши IP/UA по часам, лимит устройств |
| `events` | журнал действий |
| `user_sources` | слоты приватных источников |
| `invites` | одноразовые инвайты |

Секреты (UUID, pbk) лежат только в `servers.link`. В `import_runs`,
`events` и публичный API они не попадают.

## Маршруты Worker

| Путь | Метод | Назначение |
|---|---|---|
| `/` | GET | посадочная страница |
| `/healthz` | GET | `ok`, для внешнего мониторинга |
| `/status` | GET | страница состояния |
| `/api/v1/*` | GET | публичный read-only API + OpenAPI |
| `/api/checks/queue` | GET | очередь для Xray-агента (токен) |
| `/api/checks` | POST | результаты проверок (токен) |
| `/sub/<токен>[/режим]` | GET | персональная подписка |
| `/webhook` | POST | Telegram (секрет в заголовке) |
| `/admin/*` | GET/POST | админ-панель, cookie + CSRF |

## Решения и компромиссы

- **Один Worker вместо React + отдельного API.** Бесплатный хостинг статики
  есть, но он добавил бы вторую систему деплоя и CORS-поверхность. Админка
  серверная: быстрее грузится на телефоне и не требует сборки.
- **D1 вместо Postgres.** Управляемый Postgres без карты не найти; D1 даёт
  SQL, миграции и транзакционные батчи в тех же 5 ГБ.
- **Проверки вне Worker.** Cloudflare не даёт запускать бинарники и держать
  долгие процессы. Поэтому Xray живёт на GitHub Actions или локально, а
  Worker принимает результаты.
- **REALITY-only по умолчанию.** Остальные протоколы остаются в базе как
  история, но в публичную выдачу не попадают.
