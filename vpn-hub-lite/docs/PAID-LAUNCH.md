# Платный контур: как сервис стал продуктом

Документ описывает то, что добавлено к `vpn-hub-lite` в ноябре 2026: заказы,
оплату, выдачу доступа, возвраты, витрину и юридические страницы. Он же —
чек-лист запуска и честный список того, что ещё не сделано.

Коротко: сервис умеет принимать деньги тремя способами, сам продлевать
подписку после подтверждённой оплаты, показывать выручку и возвращать платежи.
Ни одна кнопка не выдаёт доступ без подтверждения от платёжной системы.

## 1. Что появилось в коде

Изменено: `src/bot/index.ts` (команды и события оплаты), `src/app_api.ts`
(`/api/app/buy`, `/api/app/orders`), `src/miniapp.ts` (оплата из кабинета),
`src/plans.ts` (поля витрины), `src/db.ts` + `src/turso.ts` (`meta.changes` на
Turso), `src/sub.ts` (текст для истёкшей подписки), `src/types.ts` (переменные
окружения).

### Как устроена выдача

```
кнопка «Оплатить»
   └─ orders: pending ──► провайдер ──► вебхук/успешная оплата
                                          └─► orders: paid (условный UPDATE)
                                                └─► accruals (ref = order:<id>)
                                                      └─► users.expires_at + N дней
```

Два независимых предохранителя от двойного начисления:

1. `UPDATE orders SET status='paid' WHERE status='pending'` — второй вебхук
   меняет 0 строк;
2. `accruals.ref = order:<public_id>` с `UNIQUE` — даже если первый шаг
   когда-то откажет, дни не удвоятся.

Проверяется тестами `test/orders.test.ts` (в том числе повторная доставка
уведомления и возврат).

## 2. Как включить

### 2.1 База

```bash
cd vpn-hub-lite
npx wrangler d1 migrations apply vpn-hub-lite --remote
```

Появятся `orders` и новые поля `plans`. Старые данные не затрагиваются.

### 2.2 Telegram Stars — обязательный минимум

Внутри Telegram цифровые товары продаются **только** за звёзды: так требуют
App Store и Google Play, и бот, который продаёт доступ за карту внутри
мини-приложения, просто перестаёт показываться на телефонах. Поэтому Stars —
основа кассы, а карта и крипта живут на веб-странице.

Что нужно:

1. `BOT_TOKEN` уже есть — этого достаточно, `provider_token` для звёзд пустой.
2. Команда `/paysupport` обязательна по условиям Telegram — она реализована.
3. Проверить оплату без денег: тестовое окружение Telegram
   (`https://core.telegram.org/bots/webapps#testing-mini-apps`) и тестовый бот.

Цена в звёздах считается как `price_rub / STAR_RUB` с округлением вверх.
Если нужна ровная цена («299 ⭐»), задайте её прямо в тарифе:

```sql
UPDATE plans SET price_stars = 199 WHERE code = 'month';
```

### 2.3 Crypto Pay (USDT/TON)

1. @CryptoBot → Crypto Pay → Create App → токен.
2. `npx wrangler secret put CRYPTOPAY_TOKEN`
3. Вебхук в приложении Crypto Pay: `https://<домен>/pay/webhook/cryptopay`.

Подпись проверяется по сырому телу (HMAC-SHA256, ключ — SHA256 от токена),
затем статус счёта перечитывается через API. Повторная отправка того же
уведомления не продлевает подписку.

### 2.4 ЮKassa (карта РФ и СБП)

1. Нужен магазин в ЮKassa (ИП/ООО, договор). Без юридического лица этот
   способ не подключить.
2. `npx wrangler secret put YOOKASSA_SHOP_ID`
   `npx wrangler secret put YOOKASSA_SECRET`
3. HTTP-уведомления: `https://<домен>/pay/webhook/yookassa`, события
   `payment.succeeded` и `payment.canceled`.
4. Чек 54-ФЗ: ЮKassa требует `receipt` с контактом покупателя. В сервисе вход
   через Telegram, почты нет, поэтому чек собирается только если задан
   `YOOKASSA_RECEIPT_EMAIL`. **Это ограничение нужно закрыть до первой
   продажи картой**: либо собирать email на странице оплаты, либо
   подключить фискализацию через ЮKassa. Иначе часть платежей будет
   отклоняться.

**СБП** — тот же магазин, отдельная кнопка. В запрос добавляется
`payment_method_data: { type: "sbp" }`; вебхук и проверка платежа те же, что
у карты. Включать отдельно не нужно: есть ключи ЮKassa — есть и СБП.

### 2.5 Перевод без эквайринга

Самый быстрый способ начать принимать деньги, если магазин ещё не открыт:
человек переводит сумму по номеру телефона (СБП) или на карту, а вы
подтверждаете платёж в боте.

```bash
npx wrangler secret put PAY_PHONE     # +7 900 000-00-00
npx wrangler secret put PAY_CARD      # 2200 0000 0000 0000
npx wrangler secret put PAY_RECEIVER  # имя получателя
```

Поток: тариф → «🏦 Перевод на карту» → страница `/pay/<id>` с реквизитами и
номером заказа → человек платит и отправляет `/paid ord_xxxx` → владельцу
приходит заказ с кнопками **✅ Подтвердить / ✖️ Отклонить** → при
подтверждении дни начисляются, человек получает сообщение.

Минусы, которые нужно понимать: подтверждение ручное (задержка), переводы
не видны автоматике, а возврат делается вручную (`/refund <id> manual`).
Плюс: работает без договора эквайринга и без комиссии.

### 2.6 Переменные окружения

| Переменная | Зачем | По умолчанию |
|---|---|---|
| `PAY_PROVIDERS` | какие способы включены: `stars,cryptopay,yookassa` | авто по секретам |
| `CRYPTOPAY_TOKEN` | Crypto Pay | — |
| `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET` | ЮKassa | — |
| `YOOKASSA_RECEIPT_EMAIL` | чек 54-ФЗ | — |
| `PAY_PHONE`, `PAY_CARD`, `PAY_RECEIVER` | реквизиты для перевода; пусто — способ выключен | — |
| `STAR_RUB` | сколько рублей в одной звезде | `1.3` |
| `ORDER_TTL_HOURS` | срок жизни неоплаченного счёта | `24` |
| `TRIAL_ENABLED`, `TRIAL_DAYS`, `TRIAL_DEVICES` | пробный доступ | `1`, `3`, `2` |
| `LEGAL_ENTITY`, `LEGAL_INN`, `LEGAL_EMAIL`, `LEGAL_TG` | реквизиты в документах | — |

Секреты — только `wrangler secret put`. Переменные вида `LEGAL_*` можно
поставить как `[vars]`, они не секретные.

### 2.7 Проверка после деплоя

```bash
npx wrangler deploy
```

Проверить по порядку:

1. `/` — сайт с ценами из базы;
2. `/legal/oferta` — реквизиты подставились;
3. `/buy` в боте — список тарифов и способы оплаты;
4. «Оплатить» звёздами — счёт открывается, после оплаты приходят дни;
5. `/orders` — заказ со статусом «оплачен»;
6. `/refund <ord_…>` — возврат звёзд и снятие дней;
7. `/admin/money` — выручка и список заказов.

### 2.8 Устройства и трафик

**Лимит устройств.** Считается по `users.device_limit`, по умолчанию 2
(переопределяется `DEVICE_LIMIT`, тариф может выдать больше). Устройство
определяется по User-Agent: `Happ/2.5 (iPhone; iOS 18.1)` — отдельное
устройство, тот же клиент на другом телефоне с тем же UA — нет.

Что происходит с третьим устройством:
1. оно регистрируется со `blocked=1`, `blocked_reason='limit'`;
2. подписка отдаёт заглушку **«Лимит устройств (2). Отвяжите лишнее: /app → Устройства»**;
3. в бот приходит одно сообщение в 12 часов (без спама на каждом обновлении).

Освободить место: кабинет → «Подключённые устройства» → **Отвязать**. Запись
удаляется, место сразу свободно, старое устройство при следующем запросе
зарегистрируется как новое — и, если места нет, снова получит отказ.

Записи без обращений 30 дней удаляются автоматически (`pruneDevices`,
ежедневный cron), заблокированные — через 90 дней. Это и есть «удалить
старые»: лимит не съедают телефоны, которых давно нет.

**Учёт трафика.** Worker не видит объём через туннель, поэтому счётчик
наполняет агент на своих узлах:

```bash
# на узле, раз в 5 минут
PANEL_URL=https://vpn.example CHECK_TOKEN=… NODE_NAME=de-1 \
  node tools/traffic-agent.mjs
```

Агент читает `xray api statsquery`, считает дельты по email (email в inbound
должен совпадать с `sub_token`) и отправляет их на `POST /api/traffic`.
Панель складывает в `users.traffic_used_mb`, отдаёт расход в заголовке
`subscription-userinfo` и в кабинете, а при исчерпании квоты подменяет
подписку на **«Трафик N ГБ израсходован — продлить /buy»**.

Повторная отправка пачки не удваивает расход: у каждой пачки есть `seq`,
и пачка с тем же или меньшим номером отбрасывается. Раз в 30 дней счётчик
обнуляется (`resetTrafficCounters`).

Пока агент не запущен, `used_gb` в кабинете равен нулю и помечен
`measured: false` — интерфейс не рисует выдуманный процент.

## 3. Тарифы и экономика

Стартовая сетка (правится в `plans`, код к ней не привязан):

| Код | Срок | Цена | В месяц | Устройств |
|---|---|---|---|---|
| `month` | 30 дней | 190 ₽ | 190 ₽ | 3 |
| `quarter` | 90 дней | 490 ₽ | ≈163 ₽ | 4 |
| `half` | 180 дней | 890 ₽ | ≈148 ₽ | 5 |
| `year` | 365 дней | 1490 ₽ | ≈122 ₽ | 5 |

Логика: длинный период даёт скидку за счёт предоплаты, а не за счёт качества.
Метки «−15%», «−35%» считаются относительно месячной цены и проверяются
тестом `test/pay_money.test.ts`.

### Из чего складывается маржа

Считать нужно по своей себестоимости, а не по «средней по рынку». Формула:

```
выручка за период = цена
− комиссия провайдера (Stars / эквайринг / крипто-сеть)
− налог (УСН 6% или НПД 6%, зависит от статуса)
− себестоимость трафика и серверов на этого пользователя
− доля возвратов и поддержки
= вклад в прибыль
```

Комиссии: у ЮKassa — порядка 3% (зависит от тарифа магазина), у Telegram
Stars — своя доля, точные цифры видны в таблице выплат Telegram; у Crypto Pay —
сетевой сбор плюс комиссия сервиса. **Не закладывайте «примерно ноль»:**
при цене 190 ₽ разница между 3% и 6% — это 6–11 ₽ с каждой продажи.

Практический вывод для этой сетки: годовой тариф выгоден только если
себестоимость узлов на пользователя ниже ~100 ₽/мес. Если узлы покупаются
или арендуются дороже — год за 1490 ₽ убыточен, и его нужно либо поднять,
либо ограничить трафиком.

### Пробный доступ

Сейчас новый пользователь получает 3 дня автоматически (`TRIAL_DAYS`).
Для платного продукта это работает лучше, чем «одобрение вручную»: человек
успевает проверить скорость до оплаты. Ограничения: `TRIAL_ENABLED=0`
выключает пробник, `TRIAL_DEVICES` держит его в пределах одного-двух устройств.

## 4. Возвраты и споры

- `/refund <ord_…>` — возврат через API провайдера (Stars, ЮKassa) и снятие дней.
- Crypto Pay не имеет API возврата: деньги отправляются вручную, затем
  `/refund <ord_…> manual` фиксирует возврат и снимает дни.
- Дни снимаются, но срок не уходит в прошлое — иначе следующий платёж
  «съедался» бы прошлым возвратом.
- Telegram требует обрабатывать споры по Stars самостоятельно: команда
  `/paysupport` и раздел «Оплата и возврат» на сайте — минимум, который
  должен быть до первой продажи.

Правило, которое стоит держать в голове: возврат дешевле спора. При сумме
190–1490 ₽ спор с платёжной системой стоит дороже самих денег.

## 5. Юридический контур (Россия)

Это не юридическая консультация, а список фактов, которые нельзя игнорировать.

1. **Реклама средств обхода блокировок запрещена.** Закон вступил в силу
   1 сентября 2025 года; штрафы для граждан — от 50 до 80 тыс. ₽, для
   юридических лиц выше. ФАС уже признавала рекламу VPN нарушением.
   Практический вывод: никаких таргетированных кампаний, закупки постов и
   «продвижения» сервиса. Сайт и бот — витрина продукта, но и там не стоит
   писать «обход блокировок», «доступ к запрещённым сайтам» и подобное.
   В текстах этого проекта такие формулировки убраны намеренно.
2. **Сайт может быть заблокирован.** Домены с описанием таких услуг
   попадают в реестр. Поэтому основной канал — Telegram, а сайт должен
   оставаться взаимозаменяемым (без него касса и выдача работают).
3. **Персональные данные.** Хранятся Telegram ID, username, хеши IP/UA,
   данные устройств и платежей. Нужны: политика конфиденциальности
   (есть), уведомление в РКН при обработке ПД (обязанность владельца),
   сроки хранения и порядок удаления.
4. **Оферта и возврат.** Опубликованы на `/legal/oferta` и `/legal/refund`.
   Реквизиты подставляются из `LEGAL_*`; без них документ показывает
   предупреждение. Перед продажами текст должен проверить юрист.
5. **Статус продавца.** Самозанятость (НПД) не подходит для перепродажи
   доступа третьих лиц в общем случае — нужен ИП/ООО и проверка
   применимых правил. Это решает владелец, а не код.
6. **Источники конфигураций.** Если серверы берутся из чужих публичных
   подписок, перепродажа может нарушать их условия. Коммерческий продукт
   должен опираться на собственные или официально арендованные узлы.

## 6. Чек-лист запуска

**Техника**

- [ ] миграция `0022` применена на проде;
- [ ] `BOT_TOKEN` задан, вебхук отвечает, `/paysupport` работает;
- [ ] тарифы заполнены, `price_stars` выставлены вручную для ровных цен;
- [ ] оплата звёздами проверена в тестовом окружении;
- [ ] `STAR_RUB` пересчитан под текущий курс;
- [ ] вебхуки Crypto Pay / ЮKassa зарегистрированы и проверены повторной отправкой;
- [ ] возврат по каждому провайдеру проверен хотя бы один раз;
- [ ] `/admin/money` показывает тестовый заказ;
- [ ] бэкап D1 снимается (`npm run db:export`) — заказы теперь деньги.

**Документы**

- [ ] заполнены `LEGAL_ENTITY`, `LEGAL_INN`, `LEGAL_EMAIL`, `LEGAL_TG`;
- [ ] оферта и правила возврата прочитаны юристом;
- [ ] уведомление в РКН подано (если применимо);
- [ ] в боте и на сайте нет формулировок про обход блокировок.

**Экономика**

- [ ] посчитана себестоимость узлов на пользователя;
- [ ] годовой тариф не убыточен при этой себестоимости;
- [ ] заложены возвраты (2–5% выручки) и комиссии;
- [ ] есть ответ на вопрос «что делаем, если провайдер заблокирует выплаты».

## 7. Что не реализовано и почему

1. **Автопродление и рекуррентные платежи.** Требует согласия на списания,
   хранения токена карты и отдельной юридической рамки. Сейчас подписка
   разовая, и это явно написано в интерфейсе.
2. **Баланс и внутренний кошелёк.** Раньше в кабинете рисовался «баланс 0 ₽»
   и фейковый расход трафика. Убрано: нет ledger — нет баланса. Показывать
   выдуманные числа в платном продукте хуже, чем не показывать ничего.
3. **Учёт трафика требует агента.** Механизм есть (`POST /api/traffic` +
   `tools/traffic-agent.mjs`), но данные появляются только после запуска
   агента на узлах, где email пользователя = `sub_token`. На чужих узлах,
   куда доступа нет, расход по-прежнему неизвестен.
4. **Чек 54-ФЗ без email.** См. 2.4 — нужен сбор контакта или фискализация.
5. **Налоговая отчётность.** Выручка считается в `orders`, но деклараций
   сервис не готовит.
6. **Партнёрские выплаты деньгами.** Реферальная программа начисляет дни,
   а не рубли: выплаты требуют статуса, отчётности и защиты от фрода.
7. **Мультивалютность.** Цены в рублях; Crypto Pay конвертирует по своему
   курсу на момент оплаты. Цены в USD/EUR не поддерживаются.
8. **Вебхук-очередь.** Если провайдер доставит уведомление в момент недоступной
   базы, повторная доставка сработает (провайдеры ретраят), но своей очереди
   у сервиса нет. При росте — Cloudflare Queues.

**Миграция 0022 в прод ещё не применена**: `wrangler d1 migrations apply`
упирается в исчерпанный суточный лимит чтения D1 (код 7500), сброс — в
00:00 UTC. Поэтому касса в проде пока закрыта и честно об этом говорит.

Что это значит на практике:

- `ordersReady()` = false → `/buy` пишет «оплата активируется», кнопки счёта
  не показываются;
- `/api/app/plans` отдаёт `checkout_ready: false`;
- витрина тарифов на сайте может быть пустой, если цены в базе нулевые;
- подписки, бот и выдача работают как раньше — платёжный контур просто выключен.

После сброса квоты выполнить по порядку:

```bash
cd vpn-hub-lite
npx wrangler d1 migrations apply vpn-hub-lite --remote   # 0022
npx wrangler secret put STAR_RUB                          # 1.3, если курс не задан
# затем проверка: /buy в боте и /admin/money
```

Если `orders` уже создана, повторный запуск миграции безопасен: все
выражения идемпотентны (`CREATE TABLE IF NOT EXISTS`, `INSERT OR IGNORE`),
а `UPDATE plans ... WHERE price_rub = 0` не перезапишет ваши цены.
