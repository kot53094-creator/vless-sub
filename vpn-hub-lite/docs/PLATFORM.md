# Архитектура платформы «Апельсинка VPN»

Документ этапа 3: какая архитектура выбрана, почему, что делаем дальше.
Основание — аудит `AUDIT-2026-11.md` и проверенные лимиты платформ.

## 1. Принцип

Не переписывать то, что работает. Сейчас в проде: Worker + D1 + KV +
Telegram-бот + сервис подписок + админка + агент проверки + импорт внешних
подписок. Это уже 80% требуемой платформы. Задача — довести до надёжности и
закрыть функциональные пробелы, а не заменить стек.

## 2. Целевая схема

```
                    ┌──────────────────────────────┐
Telegram ──────────▶│  Worker: API + бот + админка │
                    │  (TypeScript, Cloudflare)    │
Happ / INCY ───────▶│  /sub/<token>[/groups|…]     │
                    └───────┬──────────────┬───────┘
                            │              │
                     D1 (данные)      KV (кэш, пул,
                     + индексы         снимки, счётчики)
                            │
                    ┌───────▼────────┐
                    │ GitHub Actions │  Xray-проверки, синк, экспорт
                    └───────┬────────┘
                            │
                     VPN-узлы (вне serverless)
```

Разделение ответственности:

| Слой | Где живёт | Что хранит |
|---|---|---|
| Пользователи, тарифы, платежи, серверы | D1 | источник истины |
| Объединённый пул внешних подписок | KV | последняя рабочая версия |
| Кэш подписки | KV + `snapshots` | выдача без запросов к D1 |
| Проверки узлов | D1 `server_checks` | история и задержки |
| Секреты | Cloudflare Secrets | токены, ссылки источников, HWID |
| Тяжёлые задачи (Xray) | GitHub Actions | вне лимитов Worker |

## 3. База данных: решение

### Оставляем D1 на этом этапе

Причины, по фактам:

1. **Квоты хватает с запасом.** Бесплатный D1: 5 млн строк чтения и 100 тыс.
   записи в сутки, 5 ГБ. При 50–300 пользователях и 120 узлах реальный
   расход — десятки тысяч строк. Причина текущего отказа не установлена:
   индексы на горячих полях (`sub_token`, `status`, `enabled`, `checked_at`)
   в схеме есть, поэтому версия о полном скане маловероятна. Проверка —
   первый шаг этапа 4.
2. **Ноль сетевой задержки.** D1 находится в том же edge-окружении, что
   Worker. Postgres из другого облака добавляет 20–80 мс на каждый запрос.
3. **Нет второй квоты.** Neon/Supabase — ещё один лимит, ещё один счётчик,
   ещё одна точка отказа. Раздел 4 задания требует обратного.
4. **Переезд уже возможен.** В проекте есть слой `src/db.ts` с адаптером
   Turso/libSQL (`src/turso.ts`) и документ `MIGRATION.md`. Смена БД не
   требует переписывания бизнес-логики.

### Когда переходим на PostgreSQL

Триггеры (любой из):

- больше 500 активных подписок или 2 000 узлов;
- регулярное превышение 5 млн строк чтения в сутки после оптимизации;
- нужны транзакции между несколькими таблицами с гарантией сериализации;
- нужен полноценный BI/аналитика по истории.

Тогда: **Neon + Cloudflare Hyperdrive**. Hyperdrive на бесплатном плане даёт
100 000 запросов к БД в сутки и пул соединений — это единственный способ
ходить в Postgres из Worker без платного тарифа. Схема переносится
миграциями, D1 остаётся резервом на месяц.

Пошаговый перенос и проверка — в [PORTABILITY.md](PORTABILITY.md).

## 4. Сравнение площадок (проверено 2026-11-11)

| Площадка | Бесплатно | Постоянный процесс | Postgres | Главное ограничение | Годится |
|---|---|---|---|---|---|
| **Cloudflare Workers** | 100 тыс. запросов/сутки, 10 мс CPU, D1 5 млн строк/сутки, KV 100 тыс. чтений и 1 тыс. записей/сутки | нет (cron есть) | через Hyperdrive, 100 тыс. запросов/сутки | 10 мс CPU на вызов | **да, текущая база** |
| **Neon** | 100 проектов, 1 ГБ и 100 CU-часов на проект в месяц | нет (автосон) | да, родной | автосон и лимит вычислений | да, как БД при переезде |
| **Supabase** | 500 МБ БД, 5 ГБ egress, 2 активных проекта | нет | да | проект **засыпает после недели простоя** | как БД — с оговоркой |
| **Deno Deploy** | 1 млн запросов/месяц, 20 ГиБ egress, 10 ч CPU | нет (изоляты) | нет своего | нет постоянных процессов | нет |
| **Render** | web-сервис 512 МБ, 5 ГБ трафика | **нет: засыпает после простоя** | платно | холодный старт 30–60 с | нет для бота |
| **Vercel Hobby** | 1 млн запросов/месяц, 4 ч CPU | нет | нет | **только некоммерческое использование** | нет |

Источники: [Cloudflare Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/),
[Neon pricing](https://neon.com/pricing), [Supabase pricing](https://supabase.com/pricing),
[Deno Deploy pricing](https://deno.com/deploy/pricing), [Render pricing](https://render.com/pricing),
[Vercel Hobby](https://vercel.com/docs/plans/hobby), [Render free limitations](https://render.com/docs/free).

Вывод: ни одна из «альтернатив» не даёт одновременно постоянный процесс,
бесплатный Postgres и отсутствие карты. Cloudflare остаётся основной
площадкой; из платного рассматривается только Workers Paid $5/мес — и
только с вашего согласия, покупка не совершалась.

VPN-узлы на перечисленных площадках не размещаются: serverless и статический
хостинг для этого не предназначены.

## 5. Защита от лимитов (раздел 4 задания)

| Требование | Механизм | Статус |
|---|---|---|
| 1. Контроль использования | счётчики в KV: запросы `/sub`, записи KV, строки D1 за сутки | план |
| 2. Мониторинг лимитов | `/admin/limits` + порог 80% | план |
| 3. Предупреждение о приближении | сообщение админу в Telegram | план |
| 4. Предупреждение об ошибках и квотах | существующие `events` + новый алерт | частично |
| 5. Ограничение частоты | 60/мин на `/sub`, 5 попыток входа | **есть** |
| 6. Кэширование | KV-кэш подписки, гео на 30 дней, статус на минуту | **есть** |
| 7. Меньше запросов | снимок пула в KV, `SERVER_SQL_LIGHT`, батчи | **есть** |
| 8. Пакетная обработка | батчи по 25 в sync/health | **есть** |
| 9. Повторы с задержкой | 3 попытки загрузки источника, backoff на 429 | частично |
| 10. Защита от циклов | гейт 30 мин на синк, «два провала» на проверках | **есть** |
| 11. Очереди | очередь агента `/api/checks/queue` | **есть** |
| 12. Последняя рабочая подписка | `snapshots` 7 суток + `merge:pool` | **есть** |
| 13. Перенос Backend | `db.ts` (D1/Turso), `MIGRATION.md` | **есть** |
| 14. Экспорт базы | `/api/backup`, `wrangler d1 export` | **есть** |
| 15. Понятные сообщения | заглушки «База перегружена…» вместо 1101 | **есть** |

Пробел — пункты 1–3 и частично 4, 9. Это этап 9 плана.

## 6. Этапы 4–12

| Этап | Результат | Критерий приёмки |
|---|---|---|
| 4. БД | диагностика D1, индексы горячего пути, миграция `sync_history` | `/api/v1/status` 200, `/sub` собирается при недоступной D1 |
| 5. Backend/API | единый слой `api/` без дублей, версия v1 | OpenAPI соответствует ответам, 200 на всех маршрутах |
| 6. Бот | «Моя подписка» одним экраном, FAQ, инструкция INCY | сценарий проходит на тестовом боте |
| 7. Пользователи и подписки | единая модель `users` + `sub_versions` | просрочка/бан/продление проверены тестами |
| 8. Импорт и синхронизация | три источника, история синка, безопасное удаление | тест «источник отдал заглушку» и «источник исчез» |
| 9. Мониторинг | счётчики квот, алерты, защита от массового ложного отказа | тест: 100% узлов «мертвы» → тревога, но выдача не пустеет |
| 10. Админ | лимиты, история, источники, серверы | ручные операции пишутся в `events` |
| 11. Тесты | прогон 202 существующих + новые | `npm test` зелёный, отчёт в репозитории |
| 12. Документация и запуск | README, QUICKSTART, отчёт о запуске | деплой и проверка в INCY |

## 7. Риски

| Риск | Митигация |
|---|---|
| Источники заперты по HWID | хранить HWID в секрете, при отказе показывать причину, не удалять прошлую версию |
| Публичный репозиторий раскрывает конфиги | сделать приватным / переписать историю |
| 10 мс CPU на `/sub` | кэш, снимки, лёгкий SQL; при росте — Workers Paid $5 |
| Ложное «все узлы мертвы» | правило двух провалов и порог по доле живых |
| Один аккаунт Cloudflare | экспорт базы и переносимый слой БД |
